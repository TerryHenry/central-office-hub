Overview

Central Office Hub is a fleet-management console for many Serial Killer Terminal Server appliances ("sites") at once. Each enrolled site dials out to the hub over a signed SSH tunnel — nothing has to be opened inbound on a site's own firewall or NAT for the hub to reach it. Once enrolled, a site's ports, users, and admin state show up here automatically, and console access to any of its ports is granted and audited centrally instead of per-box.

Everything the hub does is optional from a site's point of view: a site not enrolled in any hub keeps working exactly the same, standalone. Enrolling doesn't change how the site's own local admin UI behaves, aside from the settings you explicitly choose (like disabling local SSH/web console once the hub takes over as the access path).

First login

Visit https://<hub-host>:8443 (accept the self-signed certificate warning on a fresh install) and sign in with admin / letmein0!. You'll be required to set a new password immediately, enforced by the server itself — there's no way to skip it.

Optional 2FA

Turn on two-factor authentication for this account any time from Admins → Two-Factor Authentication. Off by default.

Three account systems, not one

Hub admin accounts

Full control over this hub — sites, users, groups, and hub settings. This hub supports more than one admin account; managed in Admins. Unrelated to any site's own admin login.

Console users

Reach serial ports on enrolled sites, through group grants only. Never see this admin UI. Managed in Users.

Each site's own admin account

Separate from both of the above — the same local admin login the site has always had, standalone or not. Optionally kept in sync with this hub's own admin accounts via Sync Admins on the Sites tab, but only when you explicitly trigger it.

Web Admin UI

Dashboard

System

This hub's own resource usage — CPU, memory, disk, uptime — plus Connected Clients: everyone currently signed into a session through this hub (SSH and web console together), regardless of which site or port they're on.

Fleet Topology

A live diagram: hub → each enrolled site → that site's reported ports. Node color reflects real reachability, not just enrollment — a site node is red if its tunnel is down, and a port node is red if the site is online but that specific device isn't plugged in (when the site's firmware reports port presence; older sites without that just show reachable-or-not by tunnel state alone). Hover any node for detail.

If this hub has High Availability configured, a second node appears directly above the hub's own, linked by a dashed line: the paired controller. It shows whether this node is currently Active or Standby, and whether the health link to its peer is currently healthy.

System Information

Hostname, OS, kernel, architecture, CPU, memory, disk, Node.js version, and this app's own version — a snapshot of the hub host itself, not any site.

Sites

Each row is one enrolled edge box, identified by its tunnel public key. Its ports are reported automatically by heartbeat (every 30 seconds while it's online) — nothing to enter by hand. Reveal Port IDs shows the raw internal ID behind each port label, occasionally useful when cross-referencing a URL or API call.

Adding a site

Two ways to enroll: paste the site's own tunnel public key directly (shown on its Central Office panel), or generate a token here under Enrollment Tokens and paste that into the site instead — it fills in the hub's own address and registers the key in one step, without copying anything by hand.

Per-site actions

The ⋮ menu on each row keeps the table uncluttered:

  • Rename — changes only this site's label on the hub; doesn't touch anything on the edge box itself.
  • Upgrade Version / Request Backup — queued, applied on the site's next heartbeat, not instantly.
  • Open Admin UI — opens that site's own HTTPS admin UI in a new tab, tunneled through the same encrypted connection as its console traffic. Only shown while the site is connected. The tunnel itself never terminates or inspects the TLS inside it — it's a raw byte pipe straight to the site's own web server.
  • View Site Info — a live snapshot fetched on click (not carried on every heartbeat): hostname, mDNS name, network interfaces, public IP, connected clients, CPU/memory/disk, uptime, and versions. Only shown while the site is connected.
  • Download Backup / Restore Backup — work with whatever config backup that site last sent (or push one from a local file).
  • Configure Ports — add, edit, or remove this site's serial ports from here, including a Scan Site for Devices button that asks the site (live, over its tunnel) for its actual available device paths, instead of typing one blind. Saving replaces the site's entire port list on its next heartbeat.
  • Local Access — turn this site's own local SSH-to-serial and web console on or off, applied on its next heartbeat.
  • TFTP Server — start or stop this site's own TFTP server and change its port, upload permission, and auto-start setting, applied on its next heartbeat.
  • Upload to TFTP — pushes a file straight into this site's TFTP root directory, live, over its tunnel.
  • Sync Admins — replaces every local admin account on that site with this hub's own admin account list. Confirms before running, since it's a hard replace, not a merge.
  • Delete Site — removes it from the hub's list only. Doesn't touch the edge box itself, which can re-enroll later.

The Status column shows Admins in sync or not, computed by comparing a cryptographic fingerprint of both sides' actual admin credentials (not just usernames) — so it only ever shows green when the accounts really do match.

Hub commands unverified

Every command the hub pushes to a site (queued updates, backup restore, admin sync, port/access/TFTP config) is signed with this hub's SSH host key and verified on the site's end against whatever fingerprint that site has pinned. A site that has never pinned this hub's fingerprint refuses every pushed command outright rather than trusting one unverified — and shows Hub commands unverified in the Status column as the only visible sign, since the site itself just logs and discards the command rather than erroring back to the hub. Fix it from that site's own Central Office panel: paste this hub's fingerprint (shown above) into Hub SSH host key.

Bulk actions

Select multiple sites with the row checkboxes to Upgrade Version for Selected, Sync Admins for Selected, or Upload to TFTP for Selected in one go, instead of one at a time — the TFTP push reports success or failure per site, so one being offline doesn't block the rest.

Users

Console users reach ports through group grants only — they never see this admin UI. Each row shows which groups a user belongs to and whether their sessions are captured.

  • Groups — a user's effective access is the union of every group they're in. If two groups disagree on permission for the same port, the more permissive one wins (see Access modes & permissions).
  • Capture — when on, every session this user starts is recorded to a file, regardless of which port or site it's on. Independent of any per-port capture setting a site itself might have.

Groups

A group grants access to specific ports on specific sites — access is configured per group, never assigned to a user directly. Add a user to a group to give them everything that group grants.

Each grant carries its own read-write or read-only permission, settable right in the group's grant list, down to the individual port — not just the whole site. See Access modes & permissions for exactly what read-only restricts.

Most permissive wins

A user in two groups that both grant the same port, one read-only and one read-write, gets read-write — the effective permission for any port is the most permissive value across every group that user belongs to.

Network

Interfaces lists every network interface this hub host has, its state, and IP address, plus its Public IP as seen from the internet. Static IP and Time & DNS configure the host directly through NetworkManager/systemd — the same mechanism the appliance itself uses, so the same caution applies: a wrong address or gateway here can cut off the admin UI if you're reaching it through the interface you just changed.

System Control

Sets this hub host's own hostname.

TFTP

Off by default. Useful for pushing firmware or config files to network devices reachable from the hub host itself — separate from any TFTP server a site might run on its own network. The standard port (69) needs no extra privileges here; the service is granted that capability directly, the same way the appliance is.

Pushing to a site instead

This tab is the hub's own TFTP server. To push a file into a site's TFTP directory, or to start/stop/configure a site's own TFTP server, use that site's row menu on the Sites tab instead.

Sessions

Active Sessions

Every SSH and web console session currently open through this hub, across every site, with live Traffic (RX / TX) byte counters and how long each has been connected. Disconnect ends one immediately.

Session Captures

Byte-for-byte logs of past sessions for users with Capture turned on (Users tab) — one file per session, listed with size and last-modified time. Click a filename to download it; Delete removes it permanently.

Log

A live stream of connect/disconnect events and hub activity. Admin actions are tagged [AUDIT] right in this same stream. Download Log, at the top of the panel, saves the currently-kept history (the last 2,000 lines) as a plain-text file.

System

Password Policy

Applies to hub admin accounts only. Sites authenticate to the hub by key, not password, so this doesn't touch them.

Hub SSH Host Key

The fingerprint a site should pin in its own Central Office panel, so its tunnel connection verifies it's really talking to this hub before trusting it.

High Availability

Configures and shows the status of the standalone ha-agent process on this node — see High availability below for the full picture. In short: fill in this node's role, peer, and failover mode here and click Save Configuration; it writes the agent's config and applies most changes live, no restart needed.

TLS Certificate

Covers this admin UI's own HTTPS certificate. A self-signed one is generated automatically on first boot; upload your own to replace it. The fingerprint shown here is also what a site should pin as its own Hub TLS certificate fingerprint, separate from the SSH host key above — it protects a different set of calls (enrollment, the heartbeat, and config backups) that talk to this hub's web API rather than its tunnel listener.

Backup & Restore

Saves or replaces this hub's entire configuration — sites, users, groups, grants, admin accounts — as a single JSON file. This is the hub's own fleet configuration, separate from any individual site's backup (handled per-site from the Sites tab).

External Syslog Server

Mirrors every [AUDIT] entry to an external syslog server in real time, over UDP using the standard BSD (RFC 3164) format. Off by default. Fill in the server's host and port (514 is the usual default) and a facility, then Save Settings; Send Test Message confirms it's reaching the collector without waiting for a real event. Packets from this hub are tagged central-office:, distinct from the terminalserver: tag a site's own syslog forwarding uses — so a shared collector can tell the two apart.

Admins

My Account

Change your own hub admin password, and turn on Two-Factor Authentication (scan a QR code into an authenticator app, confirm a code, done — same flow as the appliance's admin 2FA).

Admin Accounts

This hub supports more than one admin account, managed here — the same create/rename/delete/reset-password shape as the appliance's own Admin Account tab. + Add Admin creates one with a username and password; Edit on a row renames it or resets its password (leave the password blank to keep the existing one); Delete removes it. You can't delete the account you're currently logged in as, and the hub always keeps at least one admin account — the last one can't be deleted at all, from any session.

About

Hub version, project links, and Version & Updates — checks GitHub for a newer release and applies an in-place update, with one level of rollback available from the same panel.

Access modes & permissions

Every port a site reports carries an access mode, set on the site itself and shown read-only here (in the Sites table's port list, in topology tooltips, and in the Grant dialog): Exclusive (one session at a time), Shared (read/write), Shared (first user read/write), or Shared (read-only). These describe how the port itself behaves when multiple sessions land on it — they come from the site, not from the hub.

Layered on top of that, independently, is the hub's own read-write / read-only permission per grant (see Groups). A read-only grant still lets a user open a session and watch the port's output, but their own keystrokes are never forwarded to the device — they'll see "This session is read-only; your input will not be sent to the port" right in the session, and the one exception is the detach key (Ctrl+]), which always works so a read-only session can still be left cleanly.

High availability

Optional automatic failover across two hub VMs, so the hub itself isn't a single point of failure for the whole fleet. A standalone ha-agent process runs on both nodes at all times, independent of the main hub app: it health-checks its peer, and if the peer goes unreachable past a threshold, promotes itself — final data pull, claim the shared address (or update DNS), start the hub service.

Configuring it

Everything is set from System → High Availability on each node — no file to hand-edit. Fill in:

  • Role — Primary on one VM, Secondary on the other.
  • Failover mode — Virtual IP (a floating address that moves between nodes on the same network segment, fails over in seconds) or DNS update (runs a script you supply to repoint your own DNS record, works across subnets but is only as fast as DNS caching allows).
  • Peer host and both agent ports — how the two nodes find each other's health-check endpoint.
  • Health-check and replication timing, and whether a recovered node should auto-reclaim the primary role or wait for you to click Reclaim Primary Role yourself (the default — avoids flapping between two nodes on a flaky link).

Save Configuration writes the change and, if the agent is already running on that node, applies it live — enabling/disabling, timing, and mode changes take effect immediately, no restart. A brand-new setup still needs the agent's own service started once by hand on each VM.

Per-node, not shared

Each node's configuration is its own — role, peer address, and which side owns the virtual IP are necessarily different on the two VMs. Configure each one separately with its own (mirrored) values.

Watching it

The same panel's status section shows this node's current role (Active/Standby), peer health, and last replication time. The Dashboard's fleet topology diagram also shows a small linked node above the hub for an at-a-glance check without switching tabs.

Security notes

  • Site tunnels are outbound-only from the site's side — the hub never needs an inbound connection to a site to manage it.
  • Pin a site's own SSH host key fingerprint (available on that site's Central Office panel) and this hub's own fingerprint (System tab) on both ends once, so a future connection to something impersonating either side gets rejected instead of silently trusted.
  • Pin this hub's TLS certificate fingerprint (also on the System tab, next to the SSH host key) into each site's own Central Office panel too — the SSH pin above only covers the tunnel; this one covers the separate HTTPS calls a site makes for enrollment, its heartbeat, and config backups. A config backup carries that site's admin password hashes and TOTP secrets, so this pin is what keeps them from being readable in transit.
  • A read-only grant is enforced on the hub side, in the tunnel-bridging code itself — a read-only session's keystrokes never reach the wire toward the site at all, rather than being filtered after the fact.
  • Sync Admins is only ever triggered by an explicit hub-admin action; it never runs automatically as a side effect of anything else.

Troubleshooting

A site shows Offline but I know the box is up

Check that box's own Central Office panel is still set to Managed mode and pointed at the right hub host/port — a site only appears Online while its tunnel is actually connected.

A port shows red even though the site is Online

That port's device isn't currently present on the site (only shown when the site's firmware reports port presence — older sites just reflect the site's own connection state for every port).

High Availability panel doesn't show a status section

That node's ha-agent hasn't written a status file yet — either it isn't running, or it just started. The configuration form above it still works regardless, so you can prepare the config before the agent's service is even started.
